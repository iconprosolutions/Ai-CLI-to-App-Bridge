# How AI CLI Bridge Works

> Architecture explainer for the v2 consolidated bridge. Companion docs:
> `RUNBOOK.md` (operations), `STATE.md` (project status),
> `superpowers/specs/2026-07-02-bridge-v2-design.md` (the design decisions).

## What this is

You pay flat-rate subscriptions for two AI CLIs — Claude Code (`claude`) and
Google Antigravity (`agy`). This app wraps both behind one **OpenAI-compatible
HTTP server** on port 9011, so any tool that speaks the OpenAI API (Hermes,
OpenAI SDKs, curl) can use your subscriptions as if they were API models —
with streaming, tool calls, JSON mode, per-app usage accounting, and a web
control center.

## The 30-second mental model

```
                        ┌──────────────────────────────────────────────┐
  Hermes / SDK / curl   │        provider process  (:9011)             │
  ───────────────────►  │                                              │
  POST /v1/chat/…       │  auth → validate → route → breaker → queue   │
                        │            │                                 │
  Browser               │            ▼                                 │
  ───────────────────►  │   ┌─ claude adapter ──► spawn `claude -p     │
  /dashboard/…          │   │      (stream-json)    --output-format    │
                        │   │                       stream-json` ◄─────┼── stdin: prompt
                        │   └─ agy adapter ─────► spawn `agy --print…` │
                        │                                              │
                        │  telemetry · usage ledger · capture · events │
                        └──────────────────────────────────────────────┘
```

**One process owns everything.** There is no HTTP hop between the API surface
and the engines — the "adapters" are in-process modules that spawn the CLI
binaries directly. That's why every dashboard button works: the process that
renders the kill button is the same process holding the CLI child to kill.

## Life of a request

What happens when Hermes sends
`POST /v1/chat/completions {"model":"bridge-claude-sonnet-4.6-northstar", "stream":true, ...}`:

1. **Auth** — bearer token compared timing-safely against the **named keys** in
   `.bridge-runtime/credentials.json` (v2, auto-generated by the launcher, 0600).
   The matched key (`{name, role, accountPin}`) is attached as `req.auth` so the
   request path can honor its account pin and attribute usage. See **Named API
   keys** below.
2. **Validation** — messages shape, roles, no images (400 — honestly
   unsupported, not silently degraded), `n=1` only, `logprobs` rejected.
   Ignored sampling params (`temperature` etc.) are noted and echoed back in
   `bridge_ignored_params`.
3. **Routing** — `"bridge-claude-sonnet-4.6-northstar"` (or an alias like
   `bridge-smart`) is looked up in `packages/provider/routes.json`, which maps
   route id → engine (`claude`) + upstream model (`claude-sonnet-4-6`). This
   file hot-reloads; the dashboard's Routes tab edits it through `/admin`.
4. **Account selection** — the engine's account **pool** picks a credential to
   run under (round-robin across the configured accounts; a route may *pin* a
   specific one). Each account has its own circuit breaker: if the chosen
   account recently exhausted its quota (2 consecutive quota failures) its
   circuit is *open* and it's skipped; if every account is cooling down the
   request fails immediately with `429 + Retry-After` and **no CLI is spawned**.
   Logged-out accounts are excluded (needs-login) until an operator re-probes
   them. With no `accounts.json` there is one implicit `default` account and
   this behaves exactly like a single-account bridge. See **Accounts** below.
5. **Concurrency gate** — one CLI run per account at a time (subscription-
   friendly). A short FIFO queue (depth 4, 30 s) absorbs bursts; beyond that,
   `429 engine_busy`. Multiple accounts therefore give you parallel lanes.
6. **Prompt flattening** — the OpenAI `messages` array becomes one text
   prompt with `[SYSTEM]/[USER]/[ASSISTANT]` blocks. If `tools` were sent, a
   system block teaches the model to answer with a ```json tool_calls block.
   If `response_format` was sent, a system block demands JSON.
7. **CLI invocation** — the engine adapter spawns the binary via the shared
   runner (`packages/core/cli-runner.js`):
   - prompt is written to **stdin** (argv would break past ~1 MB and leak the
     prompt to `ps`),
   - output is decoded with StringDecoder (multibyte chars can't split),
   - a byte cap, wall-clock timeout, and AbortSignal all lead to
     SIGTERM → 2 s → SIGKILL,
   - every live child sits in a registry so process shutdown reaps them all.

   **Claude** runs `claude -p --output-format stream-json
   --include-partial-messages --verbose --model <m>`. That emits NDJSON
   events: the adapter forwards `text_delta` events as live streaming deltas
   (skipping thinking/signature deltas) and reads the final `result` line for
   the authoritative text, stop reason, and **real token usage** (input +
   cache buckets + output).

   **Gemini/agy** runs `agy --print <prompt> --model <m>`. Text-only: deltas
   pass through a streaming ANSI stripper (escape codes split across chunks
   are carried, spinner `\r` frames collapsed). No token counts, so usage is
   estimated (~4 chars/token) and labeled `estimated`.
8. **Streaming back** — the provider writes SSE chunks in OpenAI's
   `chat.completion.chunk` format. A *pacer* splits chunky CLI flushes into
   word-sized deltas every 10 ms (bounded: never adds more than ~2 s total,
   stops instantly on abort, honors socket backpressure). Heartbeat comments
   (`: ping`) every 15 s keep idle streams alive while a CLI thinks.
9. **Tool calls** — if the request had `tools` and the reply is a
   ```json tool_calls block, streaming *held back* the content (up to 2 KB)
   so raw JSON never renders in the client; the provider emits proper indexed
   `tool_calls` deltas with `finish_reason: "tool_calls"` instead. Replies
   that merely *mention* tool_calls are left alone when no tools were sent.
10. **JSON enforcement** — for `response_format`, the reply is run through
    `extractJson` (fences/preamble tolerated) and, for `json_schema`, a
    dependency-free schema validator. On failure the provider makes **one**
    corrective retry ("your reply wasn't valid because …, reply with only
    corrected JSON"), then gives up with 502.
11. **Recording** — every request lands in three places:
    - **telemetry** (in-memory, last 200): powers the Overview tab,
    - **usage ledger** (`.bridge-runtime/usage/YYYY-MM.jsonl`, durable,
      bodies never written): powers the Usage tab,
    - **capture** (only when toggled on): full prompt/output + stage timings
      in a memory-only ring buffer of 50, for the Requests tab.
    An SSE event (`request.start`/`request.end`) pushes each change to any
    open dashboard.
12. **Failure mapping** — every error is a typed `BridgeError` whose `kind`
    maps to HTTP exactly once (`packages/core/errors.js`):

    | kind | comes from | HTTP |
    |---|---|---|
    | `quota` | "usage limit reached" / "exhausted your capacity" | 429 + Retry-After, `rate_limit_error` |
    | `timeout` | CLI exceeded its 5-min budget | 504 |
    | `model_not_found` | CLI rejects the model | 400 `invalid_model` |
    | `invalid_request` | e.g. prompt too big for agy's argv | 400 |
    | `spawn_failed` / `bad_output` | binary missing / garbage output | 502 |
    | `auth` | CLI account logged out / credentials expired | 503 `engine_auth_error` (marks the account needs-login, excludes it) |
    | `aborted` | client hung up or admin killed it | 499 (telemetry only; never counts against engine health) |

    Quota and timeout failures also feed the account's circuit breaker; `auth`
    failures instead flag the account as needs-login (see **Accounts** below).

## Accounts (multi-account pool)

One bridge can front **N named accounts per engine** — several Claude
subscriptions, several Antigravity sign-ins — so quota on one doesn't stop the
others, and healthy accounts run in parallel. This is optional and
zero-config: with no accounts file the bridge runs a single implicit `default`
account that leaves the CLI environment untouched (identical to the old
single-account behavior).

**Config file** — `.bridge-runtime/accounts.json` (override with
`BRIDGE_ACCOUNTS_FILE`), hot-reloaded on change and validated at boot; a bad
edit is rejected and the last good config is kept:

```json
{
  "claude": [
    { "name": "work", "dir": "accounts/claude/work" },
    { "name": "personal", "dir": "accounts/claude/personal" }
  ],
  "gemini": [
    { "name": "team", "dir": "accounts/gemini/team" }
  ]
}
```

Each account's `dir` (resolved under `.bridge-runtime/`) is that account's
isolated credential home. The adapter points the CLI at it per spawn:
**claude** via `CLAUDE_CONFIG_DIR`, **agy** via `HOME` (both verified live).
You log each account in once by running the CLI's own login flow with that env
var set; the credentials persist in the account's `dir`.

**Selection precedence** (`packages/provider/accounts.js`):
1. A route with an `account` field is **pinned** — it always uses that account
   and *fails loud* (503/429) rather than silently switching if it's
   logged-out or cooling down.
2. Otherwise **round-robin** across eligible accounts (enabled, logged-in,
   breaker not open), advancing a per-engine cursor.
3. If all accounts are open → `429` with the soonest `retryInSec`; if all are
   disabled/logged-out → `503`.

**One-shot transparent failover** — for un-pinned requests, a `quota`, `auth`,
or `spawn_failed` failure on the selected account moves the **same** request to
the next healthy account (the failed account's breaker/needs-login flag is
recorded first). This happens **at most once** and **never after bytes have
reached the client** — a mid-stream failure can't be silently retried onto
another account, so partial output is never duplicated.

**Signed-in identity** — the dashboard shows *who* is currently logged in for
each account, read straight from the CLI's config (claude:
`<CLAUDE_CONFIG_DIR>/.claude.json` → `oauthAccount`; gemini:
`<HOME>/.gemini/google_accounts.json` → `active`) — no CLI spawn, mtime-cached.
It appears as a "Signed in" row on the Overview engine cards and each Accounts-tab
card; a blank or expired login reads "not signed in". This makes swapping a
terminal's claude/gemini login immediately visible.

**Needs-login recovery** — an `auth` failure marks the account `needsLogin` and
excludes it from rotation. An operator re-logs-in that account's `dir`, then
the per-account probe (`POST /admin/accounts/:engine/:name/probe`) clears the
flag on a successful reply. `/dashboard/status` carries the full pool snapshot
(`accounts.<engine>[]` with breaker state, inflight, queued, needsLogin).

## Named API keys

The single provider key is now a set of **named keys** — one per app or
teammate — each with a `role` and an optional per-engine `accountPin`. The
keystore (`packages/provider/keys.js`) owns `credentials.json`.

**File format** — `credentials.json` v2 (0600, override with
`BRIDGE_CREDENTIALS_FILE`):

```json
{
  "version": 2,
  "keys": [
    { "name": "admin",  "role": "admin", "key": "<48 hex>", "createdAt": "…" },
    { "name": "hermes", "role": "app",   "key": "<48 hex>", "createdAt": "…",
      "accountPin": { "gemini": "main" } }
  ]
}
```

- **Roles:** `admin` keys reach `/admin/*` and dashboard mutations; `app` keys
  reach `/v1/*` only (an app key on `/admin` gets **403**). Any valid key
  authorizes `/v1`.
- **Migration:** a legacy v1 file (`{"apiKey":"…"}`) is rewritten to v2 in place
  on first load, preserving the key value as the `admin` key — so Hermes and any
  existing consumer keep working with no change. The env key
  (`PROVIDER_API_KEY`/`BRIDGE_API_KEY`, set by the launcher and tests) is layered
  on as an implicit admin key; it is never persisted or listed.
- **Account pin precedence:** `key.accountPin[engine]` → `route.account` → pool
  rotation. A key- or route-pinned request never fails over (fails loud instead).
- **Management (admin only):** `GET /admin/keys` (names/roles/pins, **never
  secrets**), `POST /admin/keys` (mint — server generates the 48-hex secret,
  returned exactly once), `DELETE /admin/keys/:name` (revoke; the last admin key
  can't be revoked). Renaming = revoke + mint.
- **Attribution:** every telemetry row and usage-ledger line carries `keyName`
  (alongside `appId` and `account`); pre-Phase-B entries render as `legacy`.

## Session continuity (flat prompt size on long conversations)

Every OpenAI-style request resends the whole history, and a fresh CLI spawn would
re-ingest all of it. Instead the bridge resumes the CLI's own conversation and
sends only the new turn. **claude only** (agy exposes no conversation id).

- After each successful **claude** completion the store
  (`packages/provider/continuity.js`) keys `sha256([routeId, normalized(messages
  + assistantReply)])` → the `session_id` from the result line, tagged with the
  serving account. In-memory, LRU 200, TTL 24h.
- On a new request whose `messages[0..n-2]` hashes to a stored entry **and** the
  owning account is the one selected, the bridge spawns `claude --resume
  <session_id>` and sends **only** the trailing turn (verified live: `--resume`
  carries prior context). Prompt size per call stays flat regardless of length.
- **Pure accelerator, never a correctness dependency.** Any mismatch — edited
  history, different route, a different account selected, or `BRIDGE_SESSIONS=0` —
  silently falls back to a normal full-prompt spawn. A *failed* resume (e.g. the
  session expired) retries the full prompt on the same account before any account
  failover. Streaming continuity is a planned follow-up (streamed calls always
  send the full prompt today, but are still remembered for later resumption).

    dashboard/        index.html + styles.css + app.js (no build step)
```

## The dashboard

Static files served at `/dashboard/`; all data comes from four endpoints:

| Tab | Reads | Acts via |
|---|---|---|
| Overview | `/dashboard/status`, `/dashboard/usage?range=today`, SSE | `/admin/breakers/:e/reset`, `/admin/requests/:id/kill`, `/admin/engines/:e/*` |
| Routes | `status.routes` | `POST/PUT/DELETE /admin/routes`, `/admin/engines/:e/probe` |
| Accounts | `status.accounts`, `usage.perAccount` | `/admin/accounts/:e/:name/{probe,enable,disable}` |
| Usage | `/dashboard/usage?range=` (by app / account / key) | — |
| Tester | `status.routes` | `POST /v1/chat/completions` (SSE or blocking) |
| Requests | `GET /admin/capture(/:id)` | `POST /admin/capture {enabled}` |
| Connect | `status.connection`, `GET /admin/keys` | stores the API key in localStorage; `POST/DELETE /admin/keys` (mint/revoke) |

Live updates: `EventSource('/dashboard/events')` triggers a throttled status
refresh on every request/breaker/health/capture event; if SSE drops, the page
falls back to 10 s polling. The header verdicts (READY/BUSY/BLOCKED/DOWN/OFF)
are derived from breaker state + health + inflight + disabled flags.

Everything under `/admin` requires an **admin-role** bearer key even when `/v1`
runs open (app-role keys get 403); `/dashboard/status|usage|events` are
unauthenticated but the server binds to 127.0.0.1 by default, so only your
machine can reach them.

## What's legacy (still in-tree, not used by default)

`claude-bridge/`, `gemini-bridge/`, `provider-bridge/` are the v1
three-process stack. They still work (tests keep them green) and are used by
`docker-compose.yml` and any old `/api/chat`-`/api/process`-`/api/contexts`
consumers. The launcher starts them only by explicit name
(`node scripts/bridge.js up claude`). The consolidated provider replaced the
v1 `provider-bridge` for all `/v1` traffic.

## How it's tested without burning quota

`tests/fixtures/fake-cli.js` is a scriptable stand-in for both CLIs: it can
emit claude's stream-json framing (with fixed token counts), agy-style ANSI
output, split multibyte characters across writes, flood, hang, or die with a
quota message — and it logs its argv so tests can assert exactly how the CLI
was invoked (or prove it *wasn't* spawned, e.g. when the breaker is open) and
which credential dir each spawn ran under (account-rotation assertions).
Six suites, ~410 assertions: `npm test`.
